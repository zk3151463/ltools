## baxia 滑块"人工拖动也被拒绝(error:csnr0k)"修复

### 现象
用户点「新开浏览器」后被 1688 baxia 风控弹出"请拖动下方滑块完成验证"，**人工拖动也提示"验证失败，点击框体重试(error:csnr0k)"**。

### 根因
- 原 `stealth.Page` + `hardenPage()` 只对**当前页**做一次 `Eval`，不跨导航。
- 用户人工在 baxia 验证页拖滑块时，验证页 JS 环境仍残留 CDP 自动化痕迹 → baxia 直接拒绝。
- 反复失败会在该 profile 上累积风险标记，越拖越失败，且代码没有"重置环境"的逃生通道。

### 修复
1. **全局跨导航注入**（`plugins/col1688/browser.go` `connect()`）：
   - 去掉 `stealth.Page`（只 patch 当前页），改用 `proto.PageEnable` + `e.page.EvalOnNewDocument(stealthJS)`（即 CDP `Page.addScriptToEvaluateOnNewDocument`）——浏览器级、每个新文档（**含 baxia 验证页**）JS 运行前强制执行。
   - 新增 `stealthJS` 常量：抹 `navigator.webdriver`/`cdc_*`/`navigator.plugins`（构造真实插件数组）/`navigator.languages`/WebGL vendor/renderer 兜底 + `Function.prototype.toString` 反检测 + `window.chrome` 兜底。
   - 连接时对当前已存在的文档再 `Eval(stealthJS)` 一次兜底。
   - 删除 `hardenPage()`（已无调用）。
2. **清理冷实例旗标**（`launch()`）：`launcher.NewUserMode()` 基础上显式 `Delete("enable-automation")`、`Delete("disable-features")`、`Delete("disable-dev-shm-usage")`。
3. **逃生通道**：
   - `browser.go` 新增 `ResetProfile()`：关闭浏览器 + 删除 `%AppData%/ltools/chrome-profile`（彻底清掉被标记的 Cookie/信任），重建空目录。
   - `service.go` 暴露 `ResetBrowserProfile()`；验证 120s 超时的日志改为"若人工拖动被拒绝，建议点「重置浏览器环境」"。
   - 前端 `Col1688Widget.tsx`：控制条加「重置浏览器环境」按钮（带 confirm）+ 说明区补充文案。

## 关键词乱码排查（先定位根因，再修）

### 现象
用户反馈"参数传递有误，汉字传入后收到的是乱码"。

### 认知修正
- 之前误判"1688 要 GBK 编码 keywords"——**错**。用户手动粘的 4 条 URL 全是 **UTF-8** 编码（帽子→`%E5%B8%BD%E5%AD%90`），且"本次测试好了"，说明 **1688 实际接受 UTF-8**，`searchURL` 的 `url.QueryEscape`（UTF-8）是对的，**不用改**。
- 真正乱码源：**1688 返回的 HTML 文档本身是 GBK 编码**（`<meta charset=gbk>` 类），`extractPage` 用 `document.documentElement.outerHTML` 拿字符串。浏览器若按页面 charset 正确解码，go-rod `evalString` 返回的 Go 字符串应是正常中文；若 1688 页面 meta charset 错标（如声明 utf-8 但实际 GBK 字节），浏览器解码出乱码 → Go 侧拿到的就是乱码。
- 1688 风控拦 HTTP 直连（诊断程序访问返回 baxia 拦截页），无法用程序直接判断编码，**必须靠浏览器侧诊断**。

### 已加诊断（plugins/col1688/browser.go `extractPage`）
- 签名加 `logf func(string)`，采集日志里打印：
  - `字符集诊断：charset=<document.characterSet> 中文样本=<前 5 个中文词>`
  - 看日志：
    - `charset=GBK` 且样本正常 → Go 字符串正常，乱码在 `parseHTML` 的 `strings`/`regexp` 处理（极少见，多半不用改）。
    - `charset=UTF-8` 但样本是乱码 → 1688 页面 meta 错标，需 Go 侧把 `outerHTML` 字节按 **GBK 重新解码**（`golang.org/x/text/encoding/simplifiedchinese.GBK` 把原始 HTTP body 字节解成 UTF-8，而不是 `outerHTML` 字符串）。
- `collectBrowser` 调用处改 `e.extractPage(src, 0, logf)`。

### 构建
- `go build .` / `go vet` / `bin/ltools.exe` EXIT 0。未改服务方法签名，bindings 无需重跑。

### 下一步（待实测）
- 跑一次采集，看日志 `字符集诊断` 行，按上面两种结果定修复方向。若需 Go 侧 GBK 重解，要改 `extractPage` 取**原始 HTTP body 字节**（CDP `Fetch`/`Network` 或 `page.Frame().MainFrame().GetContent()` 拿 body bytes），再用 `simplifiedchinese.GBK.NewDecoder()` 解码，而非 `outerHTML` 字符串。

## 崩溃修复：e.page 空指针 panic（0xc0000005）+ "没按关键词跳转"

### 现象
`task dev` 下点「开始采集」崩：
```
github.com/go-rod/rod.(*Page).Navigate(0x0, ...)   // page 是 nil
ltools/plugins/col1688.(*browserEngine).collectBrowser(browser.go:635)
```
`0xc0000005`（访问 page 内部 context，偏移 0x38）。同时用户反馈"打开浏览器时没有按关键词跳转到界面"。

### 根因
`launch()` 幂等判断 `if e.browser != nil` 太弱：
- `connect()` 里 `browser.Page()`（建页面）失败时会 `e.browser = nil` 回滚，**但 `e.page` 保留为上一次成功时的旧指针**。
- 下次 `launch()` 看到 `e.browser != nil`（或旧连接仍在）直接返回 nil，`collectBrowser` 拿着**已失效的旧 page** 去 `Navigate` → 空指针 panic；旧 page 多半已失效，导航发不出去，所以"没跳转"。

### 修复（plugins/col1688/browser.go）
1. **幂等判断加严**：`if e.browser != nil && e.page != nil` 才复用；`e.browser!=nil && e.page==nil` 时走新增的 `createPage()`（复用浏览器、重建页面，避免重开实例抢 8023 端口）。
2. **`connect` 拆分出 `createPage()`**：page 创建失败时**保留 `e.browser`**（连接本身是好的），只把 `e.page` 置 nil——下次 launch 重建页面，不再重开浏览器。
3. **新增 `navigate(url)` 辅助**：`e.page==nil` 返回明确错误，不 panic。`collectBrowser` 预热/搜索页导航改走 `navigate`；翻页块前加 `if e.page == nil` 守卫。
4. 全程 `e.page.XXX` 调用已有 nil 守卫（`humanScroll`/`extractPage`/`evalBool`/`evalJSON`/`captureScreenshot`/`dumpDiagnosis` 都查过），仅翻页块是漏网之鱼，已补。

## 澄清：「初次打开是 www.1688.com 没参数」是预热中间态，非 bug

### 现象 / 用户疑问
用户点「开始采集」后看到浏览器首次落在 `https://www.1688.com/`（首页、无 keywords 参数），以为没跳到搜索列表页。

### 根因（设计如此）
`collectBrowser` 流程：
1. `launch()` → 浏览器停在 `about:blank`
2. **预热**：`navigate("https://www.1688.com/")` → 用户看到的首页就是这一步（拟人滚动养信任度、降 baxia 灵敏度）
3. 预热完：`navigate(searchURL(o))` → **自动跳**带 `keywords` 的搜索列表页
4. 之后解析/翻页

用户已确认预期 = "保留首页预热，预热后自动跳搜索页"（即当前行为）。

### 结论
**无需改代码**。用户看到 www.1688.com 是预热中间态，约 2~4.5s（拟人滚动 + 加载）后会自动跳搜索页。
若日志有 `打开搜索页：…` 行且页面也跳了 → 正常；若停在首页没跳 → 才是 bug（多为预热时首页弹滑块 120s 超时没拖，或 `navigate(searchURL)` 报错），届时再看日志定位。

1. 跳转链接有误（baxia tmd 登录跳转），未登录时被弹到 `login.taobao.com` 白屏。

### 诚实边界 / 待实测（**关键风险点**）
1. **Wails 子窗口能否加载外部 URL**：`WebviewWindowOptions.URL` 设为 `https://www.1688.com/` 时，Wails v3 的 WebView2 是否能直接打开外部站点（而非被当作 Wails 内部路由）？现有 `search_window_service.go` 用的是 `URL: "/search"`（内部路由），**没有外部 URL 的先例**。若 Wails 不支持外部 URL，需改用 `SetURL` 或 `os/exec` 开系统浏览器（但那样就失去 JS 注入能力，退化成 html 粘贴模式）。
2. **子窗口里 `window.ltools` 是否可用**：bridge 脚本假设 Wails v3 在所有 WebView（含子窗口）都注入了 `window.ltools` 事件总线。若子窗口里没有 `window.ltools`，`__ltoolsCollect` 会走 `parent.postMessage` 兜底（需主窗口监听 postMessage 事件，当前未实现）。
3. **1688 CSP 是否允许我们注入的脚本**：bridge 是通过 `ExecJS` 注入到**已加载的 1688 页面**里执行的，不是 `<script>` 标签。`ExecJS` 走 CDP `Runtime.evaluate`，理论上能绕过 CSP（CDP 是浏览器层 API）。但 WebView2 的 `ExecJS` 实现需确认是否真走 CDP（Wails 文档未明确）。
4. **登录态**：WebView2 用 Wails 应用的独立 profile（`%AppData%/ltools/...`），首次需在子窗口里登录。之后持久。
5. **拟人轨迹没了**：go-rod 的 CDP 鼠标事件轨迹 → WebView2 里用户手动操作（最真实），但程序不再自动滚动/翻页。baxia 若检测"无程序化滚动"反而加分（更像真人）。
6. **GBK 编码问题**：上一轮的 `decodeCharset`/`rawDocBodyB64` 已删（随 go-rod 一起）。若 WebView2 按 1688 的 meta charset 正确解码，`outerHTML` 就是正常 UTF-8，无需 GBK 重解。若仍乱码，需在 `CollectCurrentPage` 里加 GBK 兜底（保留 `golang.org/x/text` 依赖就是为了这个）。

## 报错"unknown bound method id 1613137671"定位 + 双 exe 同步重建

### 现象
用户点「采集当前页」报 `ERR Binding call failed: unknown bound method id 1613137671`（= `CollectCurrentPage` 的 method id）。

### 根因（非代码 bug，是进程/二进制不同步）
1. **两个 ltools.exe 不一致**：
   - `bin/ltools.exe`（21,876,736 字节，12:04 构建）含 `CollectCurrentPage` + id `1613137671`（已字符串验证 True）。
   - 根目录 `ltools.exe`（29,466,624 字节，11:23 旧构建）**不含** `CollectCurrentPage`（字符串验证 False）。
2. **旧 ltools 进程残留**：PID 16800（来自 `bin/ltools.exe`，11:42 启动）仍在运行，内存里是**旧 Go service**（无 `CollectCurrentPage`）。即使磁盘上的 `bin/ltools.exe` 已更新成 12:04 版本，运行中的进程仍是旧的 → 前端发 `CollectCurrentPage` 调用 → 旧 Go 端不认识 method id → 报错。
3. **残留 dev 进程**：3 个 `wails3.exe` + 多个 `node.exe`/`esbuild.exe`（某次 `task dev` 被 kill 后未清），锁 go-build 缓存 + 可能用旧代码服务前端。

### method-id 机制（Wails v3）
- method-id 是 **FNV-1a 哈希**，基于方法签名（包名+方法名+参数+返回值）。
- `wails3 generate bindings` 与**运行时 Go 注册**必须基于**同一源码**，否则"前端新 binding + Go 旧注册"混合 → `unknown bound method id`。

### 处置（已执行）
1. `taskkill /F /PID 16800`（旧 ltools）→ 成功。
2. `taskkill /F /IM wails3.exe` / `esbuild.exe` → 已自动退出（"cannot terminate" = 已不存在）。
3. **同步重建两个 exe**：
   - `wails3 generate syso` → `CGO_ENABLED=1 go build -buildvcs=false -gcflags=all="-l" -o bin/ltools.exe .` EXIT 0。
   - 同参 `-o ltools.exe .` EXIT 0（**根目录也同步成新版**，避免用户误跑旧根 exe）。
   - 两者均 21,876,736 字节（12:07），字符串验证都含 `CollectCurrentPage` + id `1613137671`（True）。

### 下一步
- 用户重跑**任意一个** `ltools.exe`（bin 或根，现在都是新版），点「打开 1688」看子窗口能否加载 1688，再点「采集当前页」验证回传 + 解析。
- 若仍报错 → 确认是否又起了旧进程 / 是否跑的是别处拷贝的 exe。

## 子窗口"点按钮有时冒出新窗口"修复 + 服务实例收敛

### 现象
用户反馈：点「打开 1688」按钮**有时**会弹出**新的**子窗口（而非复用同一个），希望始终只有一个子窗口，方便渲染注入。

### 根因（Wails v3 API 特性 + 多实例）
1. **Wails v3 `WindowManager.NewWithOptions` 不按 Name 去重**：`window_manager.go:54-58` 每次调用都 `NewWindow` + `addAndRun` 直接往 `app.windows[id]` 加，**从不查重**；`Name` 仅是元数据。旧 `OpenWindow` 只靠 `if e.win != nil` 字段守卫 → 多实例 / 关闭异步 / `e.win` 被置 nil 后重开 → 冒新窗口。
   - Wails 有 `WindowManager.GetByName(name) (Window, bool)`（`window_manager.go:17`）可全局按名字查窗口，这才是去重原语。
2. **多个 `Collect1688Service` 实例**：`plugin.go` 的 `SetDataDir`（line 46）+ `NewService`（line 55）各 new 一次，加上 `main.go:213` 又 new 一个 → 2~3 个实例，各自 `registerEvents()` → 多个 `Event.On("c1688:page-html")` 监听器 + 各自独立 `pageHTMLCh`（竞争 + 泄漏）。

### 修复
1. **`browser.go` 加 `currentWindow()` 辅助**：`e.app.Window.GetByName(e.name)` 实时查全局 windows map（跨实例唯一），命中则同步 `e.win` 字段后返回 `(w, true)`。
   - `OpenWindow`：先 `currentWindow()` 命中 → 复用 `SetURL+Focus`；未命中才 `NewWithOptions`。**全局保证只有一个 c1688-window**。
   - `installBridge` / `CollectCurrentPage` / `DumpPageHTML` / `CloseWindow` / `IsWindowOpen`：全部改用 `currentWindow()` 取句柄，不再依赖可能过期的 `e.win` 字段。
2. **`plugin.go` 实例收敛**：`NewService` 改为单例（`p.service != nil` 则复用，不再 new）；新增 `Service()` 访问器返回插件持有的唯一实例（惰性创建）。
3. **`main.go:213`**：`col1688.NewCollect1688Service(app, dataDir)` → `col1688Plugin.Service()`（复用 `SetDataDir` 已建的唯一实例，不再 new 第三个）。
   - 结果：全局**一个** `Collect1688Service`，**一个** `Event.On("c1688:page-html")` 监听器，**一个** channel。

### 构建
- 先杀残留（ltools 51304 + 3× wails3 + esbuild）。
- `wails3 generate bindings` EXIT 0（82 方法）→ `npm run build` EXIT 0 → `wails3 generate syso` → `CGO_ENABLED=1 go build … bin/ltools.exe` 和根 `ltools.exe` 均 EXIT 0（21,882,368 字节，14:11）。
- 字符串验证 bin：`GetByName`/`c1688-window`/`CollectCurrentPage` 均 True。

### 诚实边界 / 待实测
- `currentWindow()` 依赖 `app.Window.GetByName` 在**子窗口关闭异步完成前**仍返回旧句柄的窗口期——`Close` 是异步的，关闭瞬间可能查到"将死"句柄，`ExecJS` 会失败/无副作用（非 panic）。用户若快速 关→开 仍可能短暂查到旧窗口；但 Wails `Remove` 在关闭事件后清 map，正常节奏下无碍。
- 仍需实测：子窗口加载外部 1688 URL 是否成功（头号风险，见上轮"待实测"）；渲染注入是否落在同一窗口。

## 导航拦截：子窗口内"链接/搜索跳转跑主窗口 / 冒新窗口"修复

### 现象
用户：子窗口里搜索或点链接触发的跳转**在当前（主）窗口打开**，而非留在子窗口内；且有时冒出新窗口。希望跳转**始终在子窗口内**，方便统一控制渲染注入。

### 根因（Wails v3 源码）
- Wails v3 webview2 层**不消费** WebView2 的 `NewWindowRequested` 事件（`internal/webview2/.../ICoreWebView2.go:687` 只有裸 `AddNewWindowRequested` COM 绑定，无 Wails 级 handler）。
- 后果：1688 页面 `target=_blank` 链接 / `window.open()` / 整页 `location` 跳转 → WebView2 默认行为 → **开新原生窗口** 或 导航泄漏到主窗口。
- 我注入的 bridge 只挂 `__ltoolsCollect`，**未拦截导航意图**。
- 且 Wails **无 CDP `addScriptToEvaluateOnNewDocument` 等价物**，`OnWindowEvent(WindowRuntimeReady)` 只在窗口创建时触发一次 → 整页导航后 JS 上下文销毁、hook 丢失。

### 修复（plugins/col1688/browser.go）
1. **bridgeJS 常量**（合并数据回传 + 导航拦截，按文档幂等 `__ltoolsBridgeInstalled`）：
   - `__ltoolsCollect`：同旧（outerHTML → `c1688:page-html`）。
   - **捕获阶段 click 拦截**：`document.addEventListener('click', h, true)`，对 `a[href]`：`target=_blank|_parent|_top` 或非 1688 域 → `preventDefault + stopPropagation + window.location.href`（当前窗口打开）。
   - **劫持 `window.open`**：url 非空且非 about:blank → `window.location.href`（当前窗口跳转）；否则返回 fake window（`{close,focus,closed,document.write}`）防调用方报错。**用户选 A：全劫持**（登录浮层也内嵌）。
   - `is1688(u)` 辅助：`/(^|\.)1688\.com$/i.test(hostname)` 判定同域。
2. **`installBridge` 改持久循环**：每 500ms `ExecJS(bridgeJS)`（幂等），直到 `closeBridgeLoop`。`missingTicks` 计数：子窗口连续 20 tick（10s）不存在 → 退出（避免窗口关闭后空转）。
   - 这是**导航 hook 跨整页导航存活的唯一手段**：每次 1688 搜索/翻页（新文档）后 500ms 内自动重注入。
3. **`windowEngine` 加字段**：`bridgeStop chan struct{}` + `bridgeRunning bool` + `bridgeMu sync.Mutex`。
   - `startBridgeLoop()`：幂等 spawn（`bridgeRunning` 守卫），`bridgeStop` 已 close 则换新 channel。
   - `closeBridgeLoop()`：`CloseWindow` 调用，close `bridgeStop`（select 防 double-close）。
   - `OpenWindow` 尾改 `go e.installBridge()` → `e.startBridgeLoop()`；`CloseWindow` 加 `e.closeBridgeLoop()`。
4. **import 加 `sync`**。

### 构建
- 杀残留（ltools 49704 + 2× wails3）→ `generate bindings`(82) → `npm run build` → `syso` → 重建 `bin/` + 根 `ltools.exe`（21,882,880 字节，14:25）全 EXIT 0。
- 字符串验证：`__ltoolsBridgeInstalled`/`__ltoolsCollect`/`is1688`/`closest` 均在二进制。

### 诚实边界 / 待实测
1. **整页导航间隙**：`window.open`/click hook 在**当前文档**内有效；整页 `location.href` 跳转（搜索提交、翻页）销毁 JS 上下文，靠 Go 端 500ms 轮询重注入恢复。**恢复前 500ms 内的跳转**可能仍走默认行为（冒新窗/跑主窗口）——这是 Wails 无 new-document 钩子的固有限制。若实测这 500ms 窗口期仍频繁冒新窗，需另寻 CDP `Page.addScriptToEvaluateOnNewDocument` 思路（但 Wails 不暴露，需 fork/patch Wails webview2 层，成本高）。
2. **`window.open` 全劫持（策略 A）**：登录浮层等 1688 弹窗若依赖真独立窗口，会被改成内嵌跳转；若登录浮层是 iframe 则不受影响。实测登录是否正常。
3. **子窗口外部 URL 加载**：用户症状"链接跳转"说明 1688 已能加载（否则没链接可点），此风险已部分自证，仍需确认整条流程。

## 兜底关窗 + JS 强化（用户反馈"还是打开新 webview 窗口"）

### 现象
JS 拦截（click + window.open 普通赋值）后，WebView2 仍冒新原生窗口。根因：Wails v3 webview2 层不接 `NewWindowRequested`，JS 普通赋值 `window.open=` 可被页面还原（`document.defaultView.open`/早期引用），且 `<form target=_blank>` 未拦。

### 修复（plugins/col1688/browser.go + service.go）
1. **路线 C 兜底（OnCreate 关窗）**：
   - `registerWindowGuard()`：`e.app.Window.OnCreate(cb)`（Wails 公开 API）。cb 里：主窗口 `Name()==""` 跳过、子窗口 `Name()=="c1688-window"` 跳过、**其余 = WebView2 冒的新窗** → `routeWindowBack(w)` 关窗。
   - `routeWindowBack`：Wails `Window` 接口**无 URL() 读法**，无法拿新窗目标 URL → 保守**只 Close() 新窗**，子窗口保持当前页。
   - 在 `registerEvents()` 里调 `registerWindowGuard()`；`onCreatedRegistered` 标志防重复注册（`bridgeMu` 保护）。
   - `SetLogf(fn)` 注入 service 的日志钩子，OnCreate 兜底时写 `c1688:log`（"检测到 WebView 新窗口（name=...），已关闭并保留子窗口"）。`service.go NewCollect1688Service` 里 `svc.engine.SetLogf(svc.logf)`。
2. **路线 B JS 强化（bridgeJS 重写）**：
   - `window.open` 改 `Object.defineProperty(obj,'open',{value:openHook, configurable:false, writable:false})` + 同时劫持 `document.defaultView.open`（压缩 bundle 走这条读原始 open）。页面**无法还原**。
   - 补 `<form target=_blank|_parent|_top>` 提交拦截（`submit` 捕获 → `preventDefault` + `location.href=action`）。
   - click 拦截保留，加 `javascript:;` href 过滤。
   - 轮询 500ms→**150ms**（`maxMissingTicks` 20→67 保持 10s 窗口缺失宽限），压缩导航后 hook 恢复窗口期。

### 构建
杀残留（ltools 44424 + node×7 + wails3×3）→ `generate bindings` → `npm run build` → `syso` → 重建 `bin/`+根 `ltools.exe`（21,888,000 字节，14:32）全 EXIT 0。字符串验证：`routeWindowBack`/`configurable`/`tagName !== 'FORM'` 均在二进制，`500 * time.Millisecond` 已不在。

### 诚实边界 / 待实测
1. **C 漏网风险**：若 WebView2 把新窗开成**独立 OS 进程**，`OnCreate` 可能收不到（Wails 只回调自己 `addAndRun` 的窗口）→ 兜底失效。实测若仍冒窗且日志无"检测到新 WebView 窗口"，即为此情形，需升级路线 A（patch Wails webview2 层接 `AddNewWindowRequested`）。
2. **routeWindowBack 只关不导回**：Wails `Window` 无 URL() 读法。冒窗被关后子窗口停在原页，用户需手动点回目标。若 Wails 后续暴露 URL 读法或 OnCreate 事件带 URL，可在此导回。
3. **defineProperty configurable:false 的副作用**：若 1688 页面自身代码对 `window.open` 做了依赖（检测/覆盖），`configurable:false` 可能触发其 try/catch 异常路径。实测登录/搜索是否正常。
