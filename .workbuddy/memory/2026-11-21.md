## 第十轮：HTTP 回退路径强制重注 bridgeJS（根治 install 循环没注到）

### 背景
第九轮（页面稳定检测 + 2s×3 重试）实测：`collectItems` 3 次尝试全
`RESOURCE_NOT_IN_CORRECT_STATE`（间隔 2s×2=4s，WebView2 未恢复）。HTTP 回退也失败
（"子窗口回传 HTML 超时"）——**根因不是 fetch 被 CSP 拦，而是 install 循环在
WebView2 bad state 时没把 bridgeJS 注到页面，`__ltoolsCollect` 不存在 → fetch 没触发**。

### 根因
`CollectCurrentPage` 的 HTTP 回退路径依赖 install 循环（80ms）已注好 bridgeJS +
suppliersJS + __ltoolsCollectURL。但 WebView2 在 `RESOURCE_NOT_IN_CORRECT_STATE`
期间，install 循环的 `ExecJS`（fire-and-forget）可能没执行（JS 引擎不可用）→
`__ltoolsCollect` 不存在 → `ExecJS(__ltoolsCollect)` 是 no-op → 回传超时。

### 修复（browser.go CollectCurrentPage，~10 行）
HTTP 回退路径在 `ExecJS(__ltoolsCollect)` 前，**强制重注**：
```go
w.ExecJS(`window.__ltoolsCollectURL=` + e.jsStringLiteral(e.htmlReturnURL()) + `;`)
w.ExecJS(bridgeJS)
w.ExecJS(suppliersJS)
time.Sleep(500 * time.Millisecond)  // 等 JS 执行
```
不等 install 循环，覆盖"bad state 时 install 循环没注到"的场景。

## 第九轮：collectItems 页面稳定检测 + 重试拉长（根治 RESOURCE_NOT_IN_CORRECT_STATE）

## 第八轮：EvalWithResult transient COM 错误重试（RESOURCE_NOT_IN_CORRECT_STATE）

### 背景
第七轮（去掉 runtimeLoaded 检查）后实测，`ExecJSResult` 真正走到 COM 提交，但报：
```
ExecuteScriptWithResult: The group or resource is not in the correct state to perform the requested operation.
```
这是 Win32 `RESOURCE_NOT_IN_CORRECT_STATE`（`0x800704CF` HRESULT），WebView2 在**双窗并发活跃**
（主窗口 + 详情页子窗口同时打开）、DPI 切换、或页面刚导航完时的**transient** 错误。
Wails 自己对 transient 错误的标准处理（Eval / SetSize / PutBounds）是"log + 容忍"，
但 `EvalWithResult` 是同步读回不能丢弃 → 需**重试**。

### 根因
`ExecuteScriptWithResult` 提交时 WebView2 内部状态不对（双窗 COM 竞争 / 导航中）→
返回 `RESOURCE_NOT_IN_CORRECT_STATE`。Wails 现有 handler 都是 fire-and-forget（丢了就丢），
`EvalWithResult` 是第一个需要"同步读回"的 → 需对 transient 错误重试。

### 修复（chromium.go `EvalWithResult`，~40 行）
提交 `ExecuteScriptWithResult` 加 **3 次尝试**（initial + 2 retries）：
- 每次失败后 `time.Sleep(200ms)` + 重新 `GetICoreWebView2_21()`（拿最新接口引用）。
- 若 `ICoreWebView2_21` 拿不到（老运行时）→ 回退 `Eval`（fire-and-forget）+ 报错。
- 若错误非 `windows.Errno`（Go 层错误如 UTF16 编码失败）→ 不重试，立即返回。
- 3 次都 transient 失败 → 返回 "ExecuteScriptWithResult: <err> (retried 2 times)"。
- 成功 → 进入正常等待 goroutine（COM 回调 close doneCh）。

`collectItems`（browser.go）的 800ms 重试保留（belt-and-suspenders：`EvalWithResult` 内部
3 次 transient 重试仍失败 → `collectItems` 800ms 后再来一轮 `ExecJSResult` → 仍失败走 HTTP 兜底）。

## 第七轮：ExecJSResult 去掉 runtimeLoaded 检查（子窗口外部页读回被早期拦截）

### 背景
第六轮实测日志：
```
[ExecJSResult] 首次读回空/失败（err=webview runtime not loaded uerr=<nil> raw=），800ms 后重试一次
[ExecJSResult] 读回供应商数据失败（根因诊断）：webview runtime not loaded
同步读回未取到数据，回退 HTTP 回传通道（__ltoolsCollect）
子窗口回传 HTML 超时（3 次重试均失败）
```
`err=webview runtime not loaded` 暴露了第六轮没考虑到的**前置拦截层**。

### 根因
`WebviewWindow.ExecJSResult`（webview_window.go:739）有 `if !w.runtimeLoaded { return "webview runtime not loaded" }` 早期返回。
`runtimeLoaded` 仅在 Wails 前端 JS runtime 发 `wails:runtime:ready` 消息时设 true（L943）。
子窗口导航到**外部 1688 URL** 后，Wails runtime JS 不注入外部页（外部页没有 `window.ltools`）→
`wails:runtime:ready` **永不发** → `runtimeLoaded` 恒 false → `ExecJSResult` 早期拦截。

对比：`ExecJS`（L704）`runtimeLoaded==false` 时把 JS **存进 pendingJS 队列**（不报错），
所以子窗口里 `w.ExecJS(suppliersJS)` 能正常注入；但 `ExecJSResult` 直接报错返回。

### 修复（webview_window.go，~10 行）
删 `ExecJSResult` 的 `runtimeLoaded` 早期返回。理由：
- COM `ExecuteScriptWithResult` 是 WebView2 **原生能力**，直接在 webview 执行任意 JS 表达式并读回结果，
  **不依赖** Wails runtime JS（window.ltools）是否加载。
- 子窗口（外部页）场景：runtime 没加载是**正常的**（外部页本就不该注入 Wails runtime），
  但 COM 读回**必须**能用。
- impl 未就绪（chromium==nil）由 `execJSResultSubmit` 兜底返回 "webview not initialized"。

## 第六轮：EvalWithResult 真·非阻塞提交（根治死锁，第五轮理论推导未实测）

### 背景
第五轮把 EvalWithResult 改成"主线程内独立 goroutine 10ms 轮询 evalDoneCh + 主线程
time.After(timeout) 兜底"。但用户实测（task dev）**仍失败**——"数据回传还是失败，
导出诊断都出问题没成功"。第五轮是**理论推导未实测**，根因未定。

### 根因重新分析（第五轮线程模型是错的）
第五轮的假设：COM 回调"在 Wails 主线程消息泵里派发"。实际：
- 所有 COM handler（含 eval handler）都是 `windows.NewCallback`（非 purego）生成 →
  WebView2 在自己的 UI 线程**同步**调用 Go 函数，**不经** Wails 主线程消息泵。
- 主线程 `runMainLoop`（mainthread_windows.go:52）是纯 GetMessage/TranslateMessage/
  DispatchMessage，**不**处理 WebView2 COM 完成事件。
- 第五轮实现：主线程内 `go func(){轮询}{}` + 主线程 `select{result / time.After}`。
  主线程被 select 阻塞 → 但回调在 WebView2 线程同步调 Go（close(done) 能执行）→
  主线程的 select 只盯 `result`（轮询 goroutine 填）和超时 → 竞态 + 大概率超时。
- 更糟：`execJSResult` 经 `InvokeSync` 派发到主线程，闭包内 `EvalWithResult` 阻塞主线程 →
  主线程消息泵停转 → 死锁风险。

### 修复（chromium.go + webview_window_windows.go + webview_window.go，三段式两段式）
**核心原则：主线程只"提交"COM 调用（非阻塞），"等待"结果在非主线程。**

1. **`edge.EvalWithResult`**（chromium.go）：改为**非阻塞提交**——
   - 提交 `ExecuteScriptWithResult` 后**立即**返回 `chan EvalResult`（容量 1）。
   - 独立 goroutine `select{doneCh / time.After(timeout)}` 等结果，写入 channel + close。
   - `EvalResult{Res string, Err error}` 导出（原 evalResult 小写，application 包读不到）。
   - 删 `evalDoneCh` 字段（改局部 doneCh，避免多调用串扰）。
   - handler 生命周期：等待 goroutine 完成（收到结果/超时）后才 handlerRelease，避免迟到回调访问已回收 handler。

2. **`windowsWebviewWindow.execJSResultSubmit`**（webview_window_windows.go）：
   - 主线程内调用（经 dispatchOnMainThread）→ `w.chromium.EvalWithResult(js, timeout)` 非阻塞拿 channel。
   - 主线程立即返回，消息泵继续转。

3. **`WebviewWindow.ExecJSResult`**（webview_window.go）：**两段式**——
   - 若 impl 实现 `execJSResultSubmit`（windows 平台）：`InvokeSync` 在主线程 submit 拿 channel，
     然后**非主线程**（调用者 goroutine）`<-resultCh` 阻塞读。主线程不被占 → COM 回调随时 close doneCh →
     等待 goroutine 填 channel → 读到结果。**死锁根治**。
   - 若 impl 只实现 `execJSResult`（server 等）：保持原同步 InvokeSync 读（调用者本就不在主线程）。

4. **`collectItems` 诊断日志**（browser.go）：失败时打完整 err 文本，区分三根因：
   - ① "ICoreWebView2_21 not supported" → 老运行时
   - ② "EvalWithResult: timeout" → 回调未派发（若第六轮修复后仍超时）
   - ③ 读回 `"[]"` / JSON 解析失败 → suppliersJS 没跑成功
   成功打 `[ExecJSResult] 读回 N 条供应商`。

5. **`DumpPageHTML` 改走 ExecJSResult**（browser.go:1490）：
   `w.ExecJSResult(document.documentElement.outerHTML||"", 10s)` 读回 HTML 写盘，不再等
   `pageHTMLCh`（HTTP 回传，1688 页 fetch 被风控拦 → 必超时）。导出诊断与数据回传同通道。

## 第五轮：EvalWithResult 主线程死锁修复（根治"没打通"）

### 背景
第四轮加了 ExecJSResult 框架层，但实测"注入子窗口 JS + 主窗口通信没打通"——
collectItems() 每次 ExecJSResult 都超时，回退 HTTP 也超时。

### 根因（同步等待跨线程 COM 回调 + 消息泵被占）
调用链：独立 goroutine（StartPages/CollectCurrentPage）→ ExecJSResult → InvokeSync →
dispatchOnMainThread（跨线程 PostMessage 到主线程）→ 主线程 execJSResult → chromium.EvalWithResult。
第四轮 EvalWithResult 里"提交 COM 回调后 `go wg.Wait()` 再 select 阻塞"——但 COM 回调只能在
Wails 主线程消息泵（GetMessage/DispatchMessage）里派发，而主线程被整个 InvokeSync 闭包占住、
消息泵停转 → 回调永不派发 → wg.Wait() 永不返回 → 每次必 ErrEvalTimeout → collectItems 恒 nil。
这是 Wails 所有现有 handler 都没踩过的坑（它们 fire-and-forget 不"等"回调，回调在 runMainLoop
里自然派发）；EvalWithResult 是第一个"同步等 COM 回调"的。

### 修复（chromium.go，~40 行）
核心：把 COM 回调完成信号**解耦到主线程消息泵**，EvalWithResult 在**主线程内**用独立 goroutine
轮询它（不让出主线程，回调能在当前消息泵循环里派发并 close，轮询 goroutine 非主线程读到即返回）。
- Chromium 结构加 `evalDoneCh chan struct{}`（每调用重建）。
- 回调 `ExecuteScriptWithResultCompleted`：`defer close(h.done)`（替代 wg.Done）。
- EvalWithResult：提交 ExecuteScriptWithResult 后，`go func(){ for{ select{case <-e.evalDoneCh:
  result<-*out; return; case <-time.After(10ms):} } }()` 轮询；主线程 `select{case r:=<-result:
  return r.res,r.err; case <-time.After(timeout): return "",ErrEvalTimeout}`。
- 去掉 sync import（不再用 WaitGroup）。

为什么通：调用方独立 goroutine 卡在 PostMessage；主线程消息泵派发我们的 fn → EvalWithResult 提交
COM 回调 → 回调在同一/后续消息泵循环派发（主线程 fn 之外空闲）→ close(done) → 轮询 goroutine（非
主线程）读到 → 结果返回 → InvokeSync 的 wg.Done() 释放调用方。主线程从未被"等回调"卡住。

## 第四轮：框架层 ExecJSResult（COM 读回 JS 结果）根治回传超时 + 逐条返回

## 第三轮：回传 HTML 超时的诊断 + CSP 兜底 + 3 次重试

### 背景
用户跑 exe 报"子窗口回传 HTML 超时（回传走 127.0.0.1:48217）"。端口 LISTENING 正常（PID 9452），
但 fetch POST 没送达 Go 端。5 种可能根因（按概率）：
1. 子窗口 JS 上下文未就绪（刚整页导航，`__ltoolsCollect`/`__ltoolsCollectURL` 还没被 80ms 循环注入）；
2. 1688 风控滑块 / baxia 拦截页，CSP 拒了我们注入的脚本；
3. 1688 页面 CSP `connect-src` 不含 `http:127.0.0.1`，拦了 fetch（滑块页必现）；
4. `__ltoolsCollect` 内部抛异常（`outerHTML` 被限制等）；
5. 端口被占 / 防火墙（极低）。

### 设计
**第一层：诊断日志**（最关键，把"为什么超时"变成可查）
- `bridgeJS.__ltoolsCollect` 开头挂 `window.__ltoolsCollectStatus = {ts, hasFn, itemsCount, url, readyState, target}`；
- `diagnoseJS` 常量：读 `__ltoolsCollectStatus` + `__ltoolsBridgeInstalled` + `__ltoolsCollect` 类型 + 当前 URL/readyState，
  sendBeacon / fetch POST 到 `/c1688/diag`（新路由）；
- Go 端 `htmlDiagHandler` 接收诊断 body，记 `[diag]` 日志（bridgeInstalled / collectFn / collectSuppliersFn /
  status{hasFn,itemsCount,url,readyState,target}）；
- `CollectCurrentPage` 第二次超时后自动 `ExecJS(diagnoseJS)`，把 root cause 打到日志。

**第二层：CSP 兜底**（fetch 被 connect-src 拦时仍能回传 items）
- `__ltoolsCollect` 的 fetch `.catch(doFallback)`：
  - `navigator.sendBeacon(target, JSON items blob)`（不受 connect-src 限制，64KB 上限够 items，html 太大不放）；
  - `new Image().src = target + '?b=' + encodeURIComponent(items)`（同样不受 connect-src 限制，服务端读 query）；
- Go 端 `htmlReturnHandler` 加 GET 分支：读 `?b=` query 重建 payload（无 html，仅 items），响应 1x1 透明 GIF。

**第三层：3 次重试**（覆盖"刚跳页 JS 上下文未就绪"）
- `CollectCurrentPage`：8s → ExecJS(__ltoolsCollect) + 等 8s；3s → ExecJS(diagnoseJS) + 等 3s；3s → ExecJS + 等 3s。
  第一次 8s（页面可能还在 load），后两次 3s（给 80ms 循环重注 bridge 的时间）。共 14s，避免无限等。
- 新增 `collectReqWait(ctx, d)` helper（select 两个 channel + time.After + ctx.Done，返回 (payload, done)）。

### 踩坑 / 注意
- Go 没有 `X if Y else Z` 三元语法（写 `8*time.Second if attempt == 0 else 3*time.Second` 会编译错），
  改成 `wait := 8s; if attempt != 0 { wait = 3s }`。
- sendBeacon 的 target 路径替换 `/c1688/html` → `/c1688/html`（保持不变），Image 兜底走 GET `?b=` 到同一路由。
- 诊断探针用 sendBeacon 优先（body-only POST，不读响应），sendBeacon 失败才退 fetch；都不受 CSP connect-src 拦
  （浏览器允许 127.0.0.1 的 beacon）。
- `__ltoolsCollectStatus` 是"最近一次 `__ltoolsCollect` 调用"的快照；diagnoseJS 在第二次超时后读它，
  能区分"bridge 根本没装"（hasFn=false）vs"装了但 items=0"（hasFn=true,itemsCount=0）vs"CSP 拦了 fetch"
  （status.target 非空但没送达 → 靠 [回传-image-fallback] 日志看是否走了兜底）。

### 构建链 EXIT 0
1. `go build .`
2. `wails3 generate bindings -clean=true -ts`
3. `npm run build`
4. CGO 双 exe（bin/ + 根目录）

### 实测待办（需用户跑 exe）
复现超时场景 → 看日志：
- `[diag] bridgeInstalled=true collectFn=function collectSuppliersFn=function url=... readyState=complete |
  status{hasFn=true,itemsCount=N,url=...,readyState=...,target=http://127.0.0.1:48217/c1688/html}` →
  bridge 装好了，items=N，target 正确 → 是 fetch 被 CSP 拦（看 `[回传-image-fallback]` 日志）；
- `[diag] bridgeInstalled=false ...` → 80ms 循环没把 bridge 注入进当前文档（页面 CSP 拒了 ExecJS /
  刚跳页 gap）→ 等页面加载完再点采集；

**双窗编排**（风控最小化）：

**JS 取数（suppliersJS 加 1688 专用分支 `from1688Result`）**：

## 第一轮：JS 取数回传 JSON + 自动多页采集（滚动 + 点下一页）

### 背景 / 诉求
用户反馈「数据没有抓取到」。根因：子窗口 HTML 确实回传回来了（本地回环 HTTP 已通），
但 Go 端 `parseHTML` 只能认"内嵌 JSON 变量 + 固定 class 的 DOM 启发式"，1688 新版结果页
的供应商数据是 React 动态渲染 / class 混淆，Go 正则命中 0 条 → 前端"未采集到数据"。
用户要求：**用 JS 在页面里直接取数据、回传 JSON 回来**，并**加翻页数量 + JS 自动点下一页 + 自动下滑滚动**。

### 设计
- **JS 取数（主路）**：`browser.go` 新增 `suppliersJS` 常量 → 页面里定义 `window.__ltoolsCollectSuppliers()`。
  三层策略（命中即返回）：
  1. 活数据对象：`window.__INITIAL_DATA__ / __INITIAL_STATE__ / __data__ / __pageData__ / __NEXT_DATA__`，
     递归找"含公司名 + (电话|地址|旺旺)"的供应商，候选键对齐 Go `collectJSON`。
  2. DOM 卡片启发式：公司名候选 class + `closest` 定位卡片容器，抽 name/phone/tel:/address。
  3. 归一化成 `[{name,phone,address,main,level,url}]`（对齐 Go `Supplier` 的 json tag）。
  结果存 `window.__ltoolsSuppliers`（JSON 字符串）。
- **回传**：`__ltoolsCollect` 的 payload 从 `{url,title,html}` 升级为 `{url,title,items,html}`；
  `pageHTMLPayload` 加 `Items []Supplier`；`finishCollect` **优先用 Items（最准）**，Items 空才回退 Go `parseHTML(html)`。
- **滚动**：`scrollLoadMoreJS` 每次 ExecJS 滚一屏，`noGrow>=2 || scrolls>6` 判到底；
  `windowEngine.ScrollToBottom(interval)` 循环执行（固定最多 8 tick / 每 tick 等 interval，因 ExecJS 是 void 读不回返回值）。
- **翻页**：`clickNextPageJS` 三策略（文本"下一页/»/›/›" → pagination 容器 → URL `pageNum`/`page` 参数 +1）；
  `windowEngine.ClickNextPage()` 执行点击（返回值读不回，靠累积指纹判断是否真翻成功）。
- **install 循环（80ms）**：整页导航销毁 window，所以每 tick 重注 `__ltoolsCollectURL` + `bridgeJS` + `suppliersJS`
  + 重置滚动状态（`__ltoolsNoGrow/__ltoolsScrolls/__ltoolsLastHeight`）+ `lightColorSchemeJS`（幂等）。
- **多页编排**：`service.go` 新增 `StartPages(opts CollectOptions) error`（Go 端 goroutine）：
  第 p 页 → `ScrollToBottom` → `CollectCurrentPage`（取数+回传）→ 累积去重（name+address）→ 推 `c1688:result` →
  MaxCount 满足则停 → 指纹（前 5 条名称）与上上页连续 2 次相同则"翻页未成功/到底"提前停 → 否则 `ClickNextPage` + 等 DelaySec。
  默认 3 页 / 间隔 2s / 上限 20 页；`Stop()` 复用 `ctx` 取消。
- **前端**：`Col1688Widget.tsx` 加 `pages`/`delaySec` 输入 + 「自动采集 N 页」按钮 + 「停止」按钮（`autoRunning` 态，
  state 回 stopped/idle 复位）；「采集当前页」（单页）保留。

### 踩坑 / 注意
- **Wails binding 字段是 PascalCase**：`CollectOptions` 生成后字段为 `Pages/DelaySec/Mode/Keyword/Category/Region/MaxCount/HTML`，
  前端调 `StartPages` 必须全字段 PascalCase 且**必填 Region/HTML**（类型要求完整 CollectOptions），否则 tsc 报
  `missing the following properties: "Region","HTML"`。camelCase 会传参丢失。
- **method 名不写进 dist**：Wails v3 用 FNV-1a method-ID 哈希在运行时解析方法，`StartPages` 字面量不出现在 bundle，
  属正常；只需确认 binding 导出存在 + 调用方 TS 编译通过。
- **ExecJS 是 void**：`ClickNextPage`/`ScrollToBottom` 读不回 JS 返回值，"是否真翻页成功"只能靠 Go 累积指纹 /
  下页数据变化间接判断；卡住检测阈值=连续 2 页指纹相同（即第 3 页才停），1688 结果页通常每页不同，故不会误停。
- **RE2**：Go 正则不支持前瞻/后顾（本次没在 Go 写新正则，JS 侧不受限）。
- 改 Go 服务方法（新增 `StartPages`）后**必须** `wails3 generate bindings -clean=true -ts` 再 `npm run build` 再双 exe。

4. `CGO_ENABLED=1; go build -buildvcs=false -gcflags=all="-l" -o bin/ltools.exe .` + 根 `ltools.exe` 同参。
